Agent Island · internals

How the Island Watches

Agent Island monitors Claude Code, Codex and Cursor sessions from a macOS notch panel. It never talks to an agent. Everything it shows is read from what those agents already write to disk, plus events they push through hooks — two independent paths that meet in one store.

The design question behind every decision here is: how do you know what an agent is doing without asking it? There is no API to call. An agent is a process that appends to a transcript, and sometimes runs a hook. So the app has exactly two ways of learning anything, and it is worth being precise about which one supplies what.

Pull · discovery

What exists

Reads the files each vendor writes. Answers which sessions are there, in what directory, how recently touched, what were they asked. Runs when the filesystem says something changed.

Push · hooks

What just happened

Agents run our hook scripts on their own events. Answers which tool is running right now, who is blocked, who needs an answer. Arrives within milliseconds; expires after 180 s so a stale event cannot pin a dormant row.

Discovery alone would be slow to react. Hooks alone would miss every session started before the app, and every vendor whose hooks do not fire. Together they cover each other's blind spot, and the panel prefers whichever is fresher.

Turning a session into somewhere you can go

the part every competing app gets wrong

A row is only useful if clicking it lands on the right terminal tab. The trick is that the answer is already in the agent process's own environment, put there by the terminal that launched it:

  • WARP_FOCUS_URL — a per-session handle Warp exports into every shell it opens. Focusing it is exact, even when eight tabs share one repository.
  • __CFBundleIdentifier — macOS stamps this into every process an app launches, so it identifies the host terminal reliably. TERM_PROGRAM does not: VS Code and Cursor both report vscode.

Both are read once per pid with a single batched ps, then cached for that process's life — a process cannot change the terminal that launched it. Rival apps resolve tabs by reading Warp's SQLite database instead, which cannot tell apart tabs sharing a working directory. Agent Island reads nothing from it, so there is no permission to grant and nothing to break when that schema changes.

When the handle is missing — a re-parented shell, a restored session, tmux over ssh — the row degrades visibly and deliberately does nothing on click, rather than raising the app and landing on an arbitrary tab. A jump that silently goes to the wrong place is worse than one that admits it cannot.

The blocking round trip

an agent waits; the notch answers

Approvals and questions run the other direction. The hook blocks its agent while polling for an answer, so every failure path has to be a fallthrough, never a hang.

Ten agents can block in the same second, so asks are queued rather than shown one-at-a-time-destructively. Questions outrank approvals — a question blocks its agent outright, while an approval can still fall back to the terminal — and an approval that gets preempted returns to the front of the queue instead of being discarded.

Why it does almost nothing most of the time

a panel that lives in the notch all day cannot poll

Polling costs the same whether or not anything happened, which is the wrong shape for this app. Agents are file-backed, so the filesystem already knows when there is something worth looking at. FSEvents reports a change and a refresh follows; the timer survives only as a backstop for what no file records, such as a process exiting without firing a hook.

Three rules keep it flat as agents multiply

  • No per-agent subprocesses. Reading one transcript's tail used to be tail | grep | tail — four processes per session, per cycle. At a hundred agents that is four hundred process creations every refresh. All of it is in-process file reading now, which also removed two places a file path was interpolated into a shell.
  • Nothing is re-read unless its bytes changed. Every cache is keyed on the file's mtime, because an append-only transcript that has not moved cannot hold a newer answer. A ten-second cache against a twenty-second refresh — which is what the title reader had — misses every single time.
  • A burst is one refresh. A floor sits under the watcher, so a hundred agents writing at once cannot mean a hundred refreshes. Nothing is dropped: an event arriving inside the window schedules the refresh at its far edge. Measured: 60 writes in two seconds produce one refresh.

Deliberate limits

things that look like gaps and are not

  • Sessions whose working directory no longer exists are hidden. They can be neither jumped to nor resumed, so the row would be a dead end. 36 of 562 Cursor sessions on this machine are in this state, mostly cleaned scratch directories.
  • A live Cursor process is not attributed to a specific session. Agents in a shared repository report the same working directory and none holds its transcript open, so liveness is inferred from append recency instead of claimed precisely.
  • Warp's database is never read. Beyond the correctness argument, opening it from inside an app bundle blocks in the kernel awaiting a consent decision that never resolves — it froze every refresh behind it until the dependency was removed.
  • Sessions older than 10 days drop off, except while blocked. A blocked agent is waiting on a human and is never hidden for being old; that is how two real work items once sat unanswered for months.
